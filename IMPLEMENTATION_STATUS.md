# IMPLEMENTATION_STATUS

Updated: 2026-11-07. Spec baseline: R3 (MG-ARTWORK-2026-1107-R3), ₹12.5 lakh base. **Not production-ready.** This is the first vertical slice of a much larger build.

## Baseline
- No repository was supplied, so this one was created empty at `artwork-saas/` (local, git, single branch). No prior code, dependencies or tests existed.
- Stack: Next.js 15 (App Router) + TypeScript 5.9, PostgreSQL 16, `sharp` for image inspection, `zod`, `vitest`. Modular monolith under `src/server/`.
- Decisions: scrypt password hashing; opaque session tokens stored hashed; tenant context resolved from an unrevoked membership, never trusted from the client; ledgers are integer paise, append-only (DB trigger), idempotent by key.
- The separate physical-printing Framer project was never accessed. The 75-surface Framer design for this product lives in a different (Framer) project and was not used as a source here.

## CMYK export, enhancement and watermarked previews (Part 23): the three base items from the quotation
- Reused from the PrintForge Preflight MVP (its code was read, not run): the FOGRA39 profile and the ESPCN 2x/4x model files. Everything else was written fresh inside this system, so it uses the same quote, hold, queue, validation, retention and audit paths as every other export.
- **CMYK** (TIFF and PDF only; PNG/JPG stay RGB, enforced in settings): sRGB to FOGRA39 through lcms in libvips, then a total-ink limit of 300% (RGB black converts to about 306%; where ink is over the limit, C/M/Y are scaled together and K is kept). TIFF is written by our own small writer (separated, 8-bit, deflate, profile embedded, resolution tags); the PDF embeds the same raster losslessly as an ICC-based CMYK image with exact Trim/Bleed boxes. Validation re-reads the stored samples and fails the job if the colour model, size, embedded profile or ink limit is wrong. Poppler (pdfimages) and Pillow read the outputs as CMYK, 300 ppi, with the 121 KB profile; poppler renders the PDF back to the expected colours. Ghostscript is not used (so no AGPL question). **No PDF/X claim** (the quotation excludes it). A4 with 3 mm bleed at 300 dpi: about 4-5 s and about 580 MB peak memory.
- **Enhancement**: off / 2x / 4x with OpenCV dnn_superres + ESPCN run as a child process (python3). Quotes are refused before any money is held if the library is missing or the enlarged image would exceed 40 megapixels. Before/after preview on a 96 px centre crop in the editor. Measured on the two sample images from the MVP (PSNR against a known original): better than a plain resize on the detailed sample (2x: 39.7 vs 34.9 dB; 4x: 34.5 vs 32.5 dB) and worse on the smooth sample (2x: 49.0 vs 59.0 dB). The editor says so and asks the customer to check the preview.
- **Watermarked preview**: every finished file gets a reduced-size (max 1000 px) JPEG with a tiled diagonal PREVIEW watermark, stored in `output_previews` (migration 014), shown on /jobs/[id] and /library, served by GET /api/outputs/[id]/preview with the same access rules as the file, deleted when the file is purged or the account is purged. The clean file still needs the signed link. The watermark text uses a server font; the Docker image installs fonts-dejavu-core and the build runs `scripts/check-runtime.ts`.
- Migrations 013 (outputs.colour) and 014 (output_previews). Library shows CMYK files as CMYK.
- Tests: tests/cmyk.test.ts, tests/enhance.test.ts, tests/preview.test.ts, additions to tests/worker.test.ts. Acceptance record (docs/OUTPUT_ACCEPTANCE.md) now includes CMYK TIFF and PDF rows.
- **Decisions for the client**: confirm FOGRA39 is the CMYK profile (the quotation says client-supplied); approve the 300% ink limit; confirm the licence of the ESPCN model files and the FOGRA39 profile (see docs/DEPENDENCIES.md); say whether enhancement carries a surcharge (today the price depends on output size only); say whether the preview watermark wording and style are acceptable.
- **Not done / not proven**: colour accuracy against a real press and approved samples; Docker build (none available here); on-screen canvas is sRGB so CMYK colours there are an approximation; ESPCN is a small model, not a high-end AI upscaler; preview look not checked on a phone; the four optional modules and PDF/X are not built (not selected in the quotation).

## Walk-in claim (Part 24, SC-030 / WF-13)
- A counter customer's job can be claimed later: the customer signs in, sends the counter **receipt number**, and the claim waits for the vendor admin. The system only matches an **email**: the signed-in customer's verified email must equal the contact the store recorded (a phone number is never matched because nothing here can verify one). Unknown receipt, another store's receipt, wrong email and phone-only records all get the same refusal, and five misses in an hour block that person for an hour.
- Approval (vendor admin only, same store) moves the walk-in projects, their source files, quote files, finished outputs and output ownership to the customer in one transaction; counter payments, receipts and ledger rows are untouched (tested by counting them before and after). Counter staff lose access to those files afterwards. Approval re-checks that the record's contact still matches. Two claimants on one record become "conflict": the admin must write a reason to approve one, and the other is rejected and told. A claimant can cancel. Rejection needs a reason.
- Corrections: the vendor admin can fix a counter record's contact (reason required, old value kept in `counter_contact_history`, audited), but not once it is claimed.
- Migration 015 (walkin_claims, counter_contact_history, claimed_by on counter_customers). Screens: /account/claim, /vendor/claims, Correct contact on /vendor/customers; the vendor home shows the number waiting. Two new email templates (claim_approved, claim_rejected).
- Tests: tests/claims.test.ts (10, with one deliberate mutation checked); Playwright tests/e2e/claims-flow.cjs: counter job, wrong receipt refused, claim waits, admin approves, files appear in the customer's library, no mobile overflow.
- Not done: phone-number verification (needs an SMS provider), an email to the vendor admin when a claim arrives, platform-side review of claims (SC-058), a screen for contact history, real-phone testing. The ownership move means a customer who deletes their account later takes those files with them under the normal account-closure rules.
